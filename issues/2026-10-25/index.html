Weekly LLM Utilization #4

LiteLLM の改ざん版配布と Agent Skills の標準化で、AI 部品の選び方と守り方が問われた週。Uber・Bayer の展開例と、大田区の AI 電話の2年目を紹介。

今週のハイライト

  • LiteLLM 1.107.0 の改ざん版が PyPI などで配布され、起動するだけで認証情報を盗むバックドアが仕込まれていた。

技術動向

LiteLLM の改ざん版が配布される：AI 部品のサプライチェーンを点検する

ソース: SafeDep・2026-10-21

悪意のある litellm 1.107.0 が、PyPI と Docker Hub / GHCR に公開された。Python のプロセスを起動するだけで、SSH 鍵、クラウドの認証情報、LLM の API キーを盗み、1時間ごとに動くバックドアを設置する。原因は開発者の GitHub CLI の認証情報の流出とされる。1.106.2 と 1.107.0rc1 / rc2 には問題がない。

LLM ゲートウェイとして LiteLLM を使うクライアントには、該当バージョンを入れていないかの確認と、認証情報の入れ替えを最優先で勧めたい。AI 系の依存パッケージは、バージョンの固定とダイジェストの検証を標準にする契機になる。本稿は SafeDep の解析にもとづき、LiteLLM の公式アドバイザリは対象週の時点で確認できていない。

Agent Skills がベンダー中立の標準に

ソース: Anthropic・2026-10-22

Anthropic は、エージェントに業務の手順を渡す形式 Agent Skills を、名称、GitHub の組織、agentskills.io のドメインごと、Linux Foundation 傘下の Agentic AI Foundation（AAIF）に寄贈した。ChatGPT、Cursor、GitHub Copilot、VS Code など70を超えるエージェント基盤が対応済みで、公開スキルは100万、インストールは約2.8億件という（同社の発表）。

クライアントには「MCP に続いて、手順を渡す形式も特定ベンダーのものではなくなった」と説明できる。社内の手順書やノウハウを Skills の形式で整えておけば、後からモデルやツールを替えても資産が残る。

Kimi K3.1 Pro：中国系オープンウェイトの有力候補と、使う前の確認事項

ソース: Moonshot・2026-10-23

Moonshot は、3T クラスで 1M トークンの文脈を持つ Kimi K3.1 Pro を発表し、11/4 までにウェイトを公開するとした。同社が公表した Terminal-Bench 4.0 のスコアは 65.7% で、Claude Opus 5.5 の 66.4% に迫る。ただしベンチマークは自社公表で、価格は未確認だ。VentureBeat はプロモーションをめぐる疑惑も報じている。

同じ週、米国土安全保障省は、連邦の民間機関に DeepSeek の製品とそれを基にしたツールを外すよう求める命令（7/24 付）を公表した（TechCrunch・2026-10-20）。民間企業は対象外だが、米国の公共部門を顧客に持つクライアントは、製品に含まれる中国製モデル（派生モデルを含む）を棚卸ししてから評価に入りたい。

ビジネス活用

OpenAI のモデルが Google Cloud でも使えるように

ソース: OpenAI・2026-10-21・OpenAI / Google Cloud・業界: クラウド

OpenAI のモデルと Codex のワークフローが、Google Cloud で使えるようになる。報道によると、Vertex AI の Model Garden で一部の顧客向けのプライベートプレビューとして始まり、既存の Google Cloud のコミット額を充当できる。Google は「主要3社のクローズドモデルをすべて使える唯一のハイパースケーラー」と位置づけている。

Azure、AWS Bedrock に続いて、GCP でも OpenAI のモデルを既存の調達と課金の枠内で選べる。クラウドの契約がモデルの選定を縛る度合いは、さらに下がる。ただし提供の範囲（プレビューか GA か）と対象のモデルは報道で食い違っており（要確認）、提案に書くときは「プレビュー段階」と添えたい。

Uber：1,000人の試行から3万人へ、伴走のエンジニアを付けて広げる

ソース: TechCrunch・2026-10-22・Uber・業界: モビリティ

Uber は全社員約3万人に ChatGPT Work を展開する。財務・オペレーション・プロダクトの各部門から1,000人が試行に参加し、早い時期の利用者の約80%はエンジニア以外だった。全社に広げる前に、AI エンジニア30人を各チームに2週間ずつ付けて、業務の自動化を手伝わせた。

「小さく試す → 伴走役を付ける → 全社に広げる」という展開の型として、そのまま提案に使える。伴走の人数と期間が明示されているので、体制の見積もりにも役立つ。一方、費用と効果の測定結果は公表されていない。

Bayer Crop Science：22のエージェントを本番で動かし、見送った機能も公開

ソース: AWS Machine Learning Blog・2026-10-23・Bayer Crop Science・業界: 農業

Bayer Crop Science は、Amazon Bedrock AgentCore の上で、取りまとめ役のエージェントと22の専門エージェントからなる意思決定の仕組みを本番で動かしている。約20の社内 API を、エージェントから呼べるツールに変換した。同社の申告では、API 統合の手間を99%超減らし、質問の約80%をエンジニアの介入なしで解決し、プロンプトキャッシュで入力のコストを20〜30%下げた。

提案に使えるのは、採用しなかった判断の記録だ。推論モードは、ツールの呼び出しや構造化出力と両立しなかったため見送ったという。「通信の成功とタスクの成功を区別せよ」という教訓も、エージェントの KPI 設計にそのまま持ち込める。数字は AWS ブログ上の自社申告である点は添えておく。

Microsoft「MAI-DxO」：精度の伸びの大半は基盤モデルから

ソース: Microsoft AI・2026-10-22・Microsoft・業界: 医療

Microsoft AI は、複数のエージェントが合議して診断する MAI-DxO を、Science 誌に発表した。NEJM の難しい症例を再現したシミュレーションで、正答率は83%だった（単独の医師は36%）。GPT-5.5 を単体で使うと72%で、MAI-DxO を重ねると約87%になる。

※筆者見解：精度の伸びの大半は基盤モデルそのものから来ており、合議の仕組みを自前で作る価値は限られる、と読める。救急の症例ではほとんど差が出なかった点も含め、医療のクライアントには「どの症例で効くか」を分けて伝えたい。

三菱電機：言葉の指示をロボットと工作機械に振り分ける

ソース: 三菱電機・2026-10-21・三菱電機・業界: 製造

三菱電機は、自然言語の指示から加工のタスクを作り、ロボットと工作機械に振り分けるフィジカル AI の技術を発表した。段取り、清掃、搬送、検査、トラブル対応をヒューマノイドに任せる構想で、2030年の実用化を目指す。製造業のクライアントに、工場の AI がどこまで来ているかを示す参照例になる。ただし研究開発の段階で、価格と提供時期は公表されていない。

規制・ガバナンス

EU は AI Act 初の整合規格、日本は「AI・デジタル改革推進会議」が始動

ソース: 欧州委員会・2026-10-19 / デジタル庁・2026-10-22・管轄: EU / JP

EU は、高リスク AI の提供者向けの品質マネジメント規格 EN 18286:2026 を官報に掲載した。準拠すれば、規格がカバーする範囲で AI Act 第17条への適合が推定される。ISO/IEC 42001 などの既存の仕組みに上乗せする設計で、取得済みの企業は差分の対応で済む。採用や与信などの高リスク用途（Annex III）への適用は 2027-12-02 に延期されており、これが準備期間の目安になる。EU 向けに採用や与信の AI を提供するクライアントには、ベンダー選定の確認項目に「EN 18286 への対応予定」を加えるよう勧めたい。

国内では AI・デジタル改革推進会議が 10/22 に初会合を開いた。日経の報道によると、AI の誤作動による損害の責任と救済のルール、開示義務の強化などを検討し、最終案は2027年6月をめどにする（要確認）。同じ週、デジタル庁は政府職員約18万人向けにエージェントの環境を提供し始め、遵守事項を定めた「源内基準」を公表した。社内でエージェントを統制する規程のひな型として使える。

連載: 導入の現場「大田区の AI 電話、目標の半分から始めた2年目」

ソース: キーマンズネット・2026-10-23・東京都大田区・業界: 自治体

大田区は、AI による電話対応を2年続けている。1年目（防災課）は担当者の対応を80%減らす目標だったが、AI だけで完結したのは約40%にとどまった。2年目は建築審査課に場所を移し、2026年10月1日から2027年2月28日まで、年約1,000時間の電話対応を30%減らすことを目標にしている。1年目の未達をどう分析し、2年目に何を変えたかを整理する。

1. 未達の原因を3つに分けた 原因は、曖昧な質問、音声認識の誤り、分岐型のシナリオの限界の3つだった。あらかじめ決めた分岐をたどる作りでは、想定から外れた質問に対応できなかった。原因を「質問の側」「聞き取りの側」「仕組みの側」に分けたことで、2年目に何を直すかが決めやすくなった。

2. 答える範囲を公開情報に絞った 2年目は、AI が答える範囲を公開されている情報に限った。そのうえで、想定 Q&A と類義語の辞書を整えた。何でも答えようとする作りをやめ、答えられる質問を確実に答える作りに切り替えたことになる。対象の課も防災から建築審査に移した（※筆者見解：問い合わせの中身が比較的定まった業務を選んだとみられる）。

3. 目標を置き直した 目標は「80%減」から「30%減」に下がった。※筆者見解：1年目の約40%という実績を踏まえ、達成できる水準に置き直したと読める。

提案に使うときの注意 音声 AI の成否は「答える範囲を限る」「言い換えの辞書を整える」の2点で決まる、というのがこの事例の示唆だ。音声ボットを提案するときは、初年度の目標を高く置きすぎないこと、未達の原因を分類して次の設計に返す仕組みを最初から入れておくことを勧めたい。なお、2年目の結果はまだ出ていない。

今週の Takeaway

  1. AI 系の依存パッケージを棚卸しする。LiteLLM の件を受け、該当バージョンの確認、認証情報の入れ替え、バージョンの固定を急ぐ。
  2. エージェントの資産は標準の形式で持つ。Agent Skills の寄贈と、OpenAI のモデルの Google Cloud 対応で、モデルやクラウドを替えても資産が残る構成を取りやすくなった。
  3. 規制への備えは「品質管理」と「責任分担」の2軸で進める。EU の EN 18286 と、国内の責任・救済ルールの議論が同じ週に動いた。
